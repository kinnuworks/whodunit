c54575368397 cut max_steps to 3, leaving no budget to recover from truncated batch tool calls

Commit c54575368397 reduced max_steps from 8 to 3 and max_tokens from 300 to 150, meaning the agent has no spare model calls to recover when a batched tool call is truncated.1

In the failing run, the 150-token cap causes the third LLM response at acbf23c5 to be cut off mid-JSON, so the second issue_refund call arrives with only order_id and no amount or reason, producing the error at 6e23affa.2 3

Similarly, the first LLM call at 0abc1926 was truncated so that the second lookup_order call arrived with no arguments, causing the error at 4d831c6b and forcing an extra recovery call.4 5

That recovery call consumed the third and final model slot at 0da4439e just to re-look up order 6006, leaving no calls left after 6e23affa to retry the failed refund.6 7 2

In the passing run at b467d5b0fed2, max_steps was 8 and max_tokens was 300, so both lookup_order calls fit in one response at 1e654c3a and both issue_refund calls fit in one response at 8172ddce with no errors.8 9 10

Because truncation depends on how the model serialises multiple tool calls into one response, failures are intermittent—matching the ~14% failure rate observed from c54575368397 onward across checkpoint d098c3973305.1 11
